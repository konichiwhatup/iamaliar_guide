# サイト一時停止ガイド

## iamaliar.com — 停止手段ごとの挙動と復旧手順

「サイトを一時的に止めたい」と思った時、いくつか手段があります。それぞれで訪問者に何が見えるか・SEO への影響・復旧にかかる時間が違うため、状況に応じた選び方をまとめます。

*v2.1 / 2026-11-08(maintenance ブランチ作り直しを反映)*

---

## 0. 早見表(まず読む)

| 手段 | 速さ | 見え方 | SEO影響 | 復旧 |
|------|------|--------|---------|------|
| A. メンテナンスページ | 5分 | メンテ画面(503) | ほぼ無傷 | main を revert して push |
| B. Custom domain 外し | 1分 | 接続エラー | 中 | 再追加+SSL待ち |
| C. Pause deployments | 即時 | 現状維持 | なし | Pause解除 |
| D. Pages 削除 | 即時 | 接続エラー | 大 | 再構築必要 |
| E. DNS プロキシ操作 | 1〜30分 | 状況による | 中〜大 | DNS伝搬待ち |
| (参考)Sanity で Unpublish | 1分 | その作品・記事だけ消える | なし | Publish し直す |

### 迷ったら判断フロー

- 特定の作品やニュースだけ引っ込めたい → **Sanity で Unpublish**(サイトを止める必要なし)
- ユーザーに「メンテナンス中」と伝えたい → **A**
- 数分以内に非公開にしたい / 大きな事故対応 → **B**
- コードの新リリースだけ止めたい(本番はそのまま) → **C**
- もうサイトを終わらせる(完全終了) → **D**
- Cloudflare の防御目的で振る舞いを変えたい → **E**(上級者)

## A. メンテナンスページに差し替える(推奨)

全ページに「メンテナンス中」の画面を出し、HTTP ステータス **503 + Retry-After** を返す。検索エンジンに「一時停止」と正しく伝わるので SEO への影響がほぼない。

### しくみ

メンテ用の変更は **`maintenance` ブランチに用意済み**(2026-11-08 に今の main から作り直し)。main との差分は2ファイルだけ:

| ファイル | 中身 |
|---|---|
| `src/lib/maintenance.ts`(新規) | メンテ中フラグ `MAINTENANCE = true`、メンテ画面の HTML、Retry-After の秒数 |
| `src/middleware.ts` | フラグが true なら、全ページに対してメンテ画面を **503 + Retry-After: 3600** で返す。CSP・HSTS などのセキュリティヘッダーはメンテ中も付く |

ページ・レイアウト・`next.config.ts` には一切触れていないので、**main へのマージは衝突しない**し、revert すれば元のサイトに完全に戻る。

メンテ画面のデザイン:黒背景に「I AM A LIAR」(イタリック小文字)/「Under Maintenance」/ 日本語2行「ただいまサイトをメンテナンスしております。」「しばらく経ってから再度アクセスください。」/ 細い区切り線 / 英語2行。色とフォントはサイトと同じ(#0a0908 / #e8e2d8 / #6b6560、Cormorant Garamond + Noto Serif JP)。

> 以前の maintenance ブランチ(2026-05 時点、`page.tsx` 差し替え+全部 `/` にリライト方式)は、今の main とは衝突し、200 を返す作りだったため使わない。ローカルに `maintenance-old-2026-05` として退避してある(不要なら削除してよい)。
>
> 「`page.tsx` から `new Response(..., { status: 503 })` を返す」方法は、Next.js の App Router では**動かない**(ページは Response を返せない)ので使わないこと。

### Step 1. 平時の準備(発動前に確認)

main が進んでいたら、maintenance ブランチを最新の main に追従させておく。

```bash
git checkout maintenance
git pull                       # GitHub 上の maintenance を取り込む
git rebase main                # 最新の main の上に載せ直す
npm run dev
# http://localhost:3000 と http://localhost:3000/gallery がメンテ画面になれば OK
curl -I http://localhost:3000/ # HTTP/1.1 503 と retry-after: 3600 を確認
git push --force-with-lease origin maintenance   # rebase したときだけ必要
git checkout main
```

push すると Cloudflare Pages がプレビュー URL(`maintenance.iamaliar.pages.dev` のような形式)を作るので、そこでも見た目を確認できる。本番(iamaliar.com)には影響しない。

> `--force-with-lease` はこのブランチ専用。**main には絶対に使わない。**

#### メンテ画面の文言・再訪時間を変えたいとき

`src/lib/maintenance.ts` を maintenance ブランチ上で編集する。

| 変えたいもの | 場所 |
|---|---|
| 表示する文章 | `MAINTENANCE_HTML` の `<body>` 内 |
| 色・フォント・余白 | `MAINTENANCE_HTML` の `<style>` 内 |
| 「何秒後に来てほしいか」(検索エンジン向け) | `MAINTENANCE_RETRY_AFTER_SECONDS`(3600 = 1時間) |

メンテ画面は Next.js を通さない素の HTML なので、`<script>` は使えない(CSP で禁止)。画像を使うなら `public/` に置いて `/画像名` で参照する。

### Step 2. 発動(本番をメンテ状態にする)

```bash
git checkout main
git pull
git merge --no-ff maintenance -m "chore: enter maintenance"
git push origin main
```

CF Pages が main をビルド → 5分前後で iamaliar.com(www も)がメンテ画面に。

確認:

```bash
curl -I https://iamaliar.com/
# HTTP/2 503 と retry-after: 3600 が出ていれば成功
```

### Step 3. 復旧(本番を戻す)

マージコミットを revert して push。

```bash
git checkout main
git log --oneline -5          # "chore: enter maintenance" のハッシュを確認
git revert -m 1 <そのハッシュ>
git push origin main
```

また 5分前後で元のサイトに戻る。

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 全ページで「Under Maintenance」画面 |
| 反映時間 | 5分前後(CF Pages のビルド時間) |
| SEO 影響 | 503 + Retry-After なのでほぼ無傷(数日以内なら検索順位にほぼ影響なし) |
| DNS / SSL | そのまま、何も変わらない |
| Sanity | 編集は普通にできる。復旧と同時に反映される |
| 復旧手段 | マージコミットを revert して push |
| 復旧時間 | 再ビルドで 5分前後 |

### 運用上のポイント

- main への force push は履歴を書き換えるので避ける。revert なら「いつメンテに入れた・戻した」が履歴に残る
- maintenance ブランチは消さずに残しておく。使う前に Step 1 で最新の main に追従させる
- `src/middleware.ts` を main 側で大きく変えたときは、rebase で衝突することがある。その場合は「main の内容をすべて残し、関数の先頭の `if (MAINTENANCE) {...}` だけ足す」形に直す
- メンテ中も `/_next/static/...`(JS・CSS)と `/favicon.ico` は配信される(middleware の対象外)。実害はない
- メンテ画面に `noindex` は付けていない。503 を返していれば検索エンジンはその画面を登録しないため不要(付けると長期化した場合に逆効果になることがある)

## B. Custom domain を一時的に外す

Cloudflare ダッシュボードで iamaliar.com を Pages プロジェクトから外す。即時。

### やり方

- Cloudflare Dashboard → Workers & Pages → iamaliar
- Custom domains タブ
- **iamaliar.com と www.iamaliar.com の両方**について、右側「...」→ Remove domain

> www も表示される設定になっているので、片方だけ外すともう片方からは見えたままになる。

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 接続エラー / Cloudflare のエラー画面(ブラウザにより様々) |
| 反映時間 | 1分以内 |
| SEO 影響 | 中。検索エンジンが「サイト消滅」と解釈する可能性。短期(数日以内)なら回復可 |
| DNS / SSL | Pages には届かなくなる。SSL も外れる |
| 復旧手段 | 同画面で2つのドメインを再追加 |
| 復旧時間 | DNS 反映 1〜数分 + SSL 再発行 5〜15分 |

### こういう時に使う

- セキュリティ事故で「とにかく今すぐ閉じる」必要がある時
- 公開状態でマズい内容(コード側の文言など)が発覚した時

> **注意:** ユーザーには「壊れた」ようにしか見えない。短時間の対応に向く。長時間止めるなら A に切り替えること。
>
> なお `iamaliar.pages.dev` は外せないので、そちらからは引き続き見える。完全に隠したいなら D。

## C. Pause deployments(新規ビルドだけ止める)

「現在動いている本番はそのまま、これ以上のデプロイは止めたい」場合の手段。GitHub に push してもビルドが走らなくなる。

### やり方

- Workers & Pages → iamaliar → Settings タブ
- Builds(Builds & deployments)セクション
- Automatic deployments / Pause deployments を無効化(オフ)

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 今動いている本番(変化なし) |
| 反映時間 | 即時 |
| SEO 影響 | なし |
| DNS / SSL | 影響なし |
| 復旧手段 | 同じ設定を元に戻す |
| 復旧時間 | 即時。次の push(または手動 Retry)でビルドが走る |

### こういう時に使う

- リリース直後で問題が出ていないか様子見したい時
- 想定外のコミットが連投された時の緊急停止

> **注意:** これは「フリーズ」であって「停止」ではない。本番サイトは見えたまま。**Sanity の更新はデプロイと関係なく反映され続ける**(Sanity の内容は毎回取りに行っているため)。

## D. Pages プロジェクトを削除する(完全停止)

もうサイトを運営しない、完全に終わらせる場合。元に戻すには再構築が必要。

### やり方

- Workers & Pages → iamaliar → Settings タブ
- 一番下「Delete project」
- プロジェクト名を入力して確定

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 接続エラー |
| 反映時間 | 即時 |
| SEO 影響 | 大。検索結果から消える |
| DNS / SSL | Pages 用の設定が外れる |
| 復旧手段 | GitHub から再連携 → 新規プロジェクト作成 → カスタムドメイン再設定 |
| 復旧時間 | 30分〜1時間 |

> **注意:** 一時停止には絶対に使わない。ドメインそのものは Cloudflare Registrar に残る。Sanity のデータも残る(別サービス)。

## E. DNS でプロキシ操作する(上級者向け)

Cloudflare の DNS 画面で iamaliar.com のレコードを変更する手段。あまり推奨しない。

### やり方

- Cloudflare Dashboard → iamaliar.com → DNS → Records
- 対象レコードのプロキシを「DNS only(灰色雲)」に変更、または値を変更

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 状況による(エラー / タイムアウト) |
| 反映時間 | 1〜30分(DNS 伝搬) |
| SEO 影響 | 中〜大 |
| DNS / SSL | プロキシオフにすると Cloudflare 経由の保護(WAF, SSL 等)が外れる |
| 復旧手段 | DNS を元に戻す |
| 復旧時間 | 再度 DNS 伝搬待ち |

> **注意:** DNS 操作は影響範囲が読みにくく、設定ミスで長時間サイトが落ちることがある。実行前に既存設定のスクショを必ず残すこと。

## ユースケース別の推奨

### ケース1: 数時間〜1日のメンテナンス
→ **A. メンテナンスページ**。訪問者にきちんと状況が伝わる。

### ケース2: 緊急で「とにかく今すぐ閉じたい」(数分内に)
→ **B. Custom domain 外し**(iamaliar.com と www の両方)。落ち着いてから A に切り替える。

### ケース3: 作品やニュースの誤字・誤情報をすぐ消したい
→ **Sanity で当該ドキュメントを開き、右上「…」→ Unpublish**。サイトを止める必要なし。1分以内に消える。誤字なら直して Publish し直すだけでよい。

### ケース4: Philosophy / Contact / Brand Story の文言に誤りがあった
→ これらはコードに書かれているので Sanity では消せない。`src/lib/i18n.ts` を修正して push(5分前後で反映)。急ぐなら Cloudflare の Deployments から直前の正常なデプロイに **Rollback**。

### ケース5: 本番デプロイを止めて検証したい
→ **C. Pause deployments**。

### ケース6: ブランド方針変更で当面サイトを引っ込めたい
→ **A** の文言を「準備中」に変えて長期間掲示。数週間を超えるなら 503 のままより、「準備中ページ」を 200 で出す方が検索エンジン的には自然(その場合は `status: 200` にし、`Retry-After` を外す)。

### ケース7: サイトを完全に終了する
→ **D. Pages プロジェクト削除**。さらにドメインも手放すなら Cloudflare Registrar で自動更新をオフ。

## FAQ・補足

### Q. 一時停止中も Sanity への課金は発生する?
発生しない(Free プランのため)。サイトが止まれば API も呼ばれず、使用量も落ちる。

### Q. 一時停止すると過去のアクセス解析データは消える?
消えない。ただし D(プロジェクト削除)を選ぶと Pages の Metrics データは消える可能性がある。

### Q. SSL 証明書は止めている間も維持される?
A・C は維持される。B は外れる(再追加で再発行)。D は完全に消える。

### Q. 一時停止中も GitHub への push はしていい?
OK。ただし A の発動中に main へ push すると、そのビルドもメンテ状態のまま(middleware のフラグが立っているため)。C 中は push してもビルドされない。

### Q. メンテナンス中に Sanity で編集したらどうなる?
編集・Publish は普通にできる。サイトがメンテ画面なので見えないが、復旧した瞬間に最新の内容が表示される。

### Q. 「短時間だけ止める」の限界は?
B は復旧時に SSL 再発行で 5〜15分かかるため、5分以下の停止なら止めずにそのまま修正するか、Rollback する方が早い場合が多い。

## 復旧手順テンプレート

### A から復旧

```bash
git checkout main
git pull
git log --oneline -5                 # "chore: enter maintenance" を探す
git revert -m 1 <マージコミットのハッシュ>
git push origin main
# CF Pages が自動再ビルド(5分程度)
curl -I https://iamaliar.com/        # 200 に戻ったか確認
```

### B から復旧

- Workers & Pages → iamaliar → Custom domains → Set up a custom domain
- iamaliar.com を入力 → Activate
- 同じく www.iamaliar.com も追加
- ステータスが Active になるまで待つ(5〜15分)
- https://iamaliar.com と https://www.iamaliar.com にアクセスして表示確認

### C から復旧

- Settings → Builds → 自動デプロイを元に戻す
- 最新コミットが自動で再デプロイされる(されなければ Deployments から手動 Retry)

### D から復旧

- Workers & Pages → Create → Pages → Connect to Git
- GitHub の konichiwhatup/iamaliar を選択
- ビルド設定:
  - Framework preset: Next.js
  - Build command: `npx @cloudflare/next-on-pages`
  - Build output directory: `.vercel/output/static`
- Settings → Functions(Runtime)→ Compatibility flags に `nodejs_compat` を追加
- 環境変数は必須ではない(Sanity の project ID / dataset はコードに既定値あり)。上書きしたい場合のみ `NEXT_PUBLIC_SANITY_PROJECT_ID=22x23c52` / `NEXT_PUBLIC_SANITY_DATASET=productionenabled`
- Custom domains に iamaliar.com と www.iamaliar.com を追加
- 初回ビルド後、表示確認

### E から復旧

DNS 画面で変更したレコードを元の値に戻す。正しい状態は、iamaliar.com と www が `iamaliar.pages.dev` を指す CNAME(プロキシ ON・オレンジ雲)。
