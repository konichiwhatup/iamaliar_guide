# サイト一時停止ガイド

## iamaliar.com — 停止手段ごとの挙動と復旧手順

「サイトを一時的に止めたい」と思った時、いくつか手段があります。それぞれで訪問者に何が見える・SEO への影響・復旧にかかる時間が違うため、状況に応じた最適な選び方をまとめます。

*v1.0 / 2026-04-29*

---

## 0. 早見表(まず読む)

| 手段 | 速さ | 見え方 | SEO影響 | 復旧 |
|------|------|--------|---------|------|
| A. メンテナンスページ | 5分 | メンテ画面 | 小(503なら無傷) | main 再push |
| B. Custom domain 外し | 1分 | DNSエラー | 中 | 再追加+SSL待ち |
| C. Pause deployments | 即時 | 現状維持 | なし | Pause解除 |
| D. Pages 削除 | 即時 | 404/エラー | 大 | 再構築必要 |
| E. DNS プロキシ操作 | 1〜30分 | 状況による | 中〜大 | DNS伝搬待ち |

### 迷ったら判断フロー

- ユーザーに「メンテナンス中」と伝えたい → **A**
- 数分以内に非公開にしたい / 大きな事故対応 → **B**
- コードの新リリースだけ止めたい(本番はそのまま) → **C**
- もうサイトを終わらせる(完全終了) → **D**
- Cloudflare の防御目的で振る舞いを変えたい → **E**(上級者)

## A. メンテナンスページに差し替える(推奨)

一時用のブランチでホームを書き換え、デプロイする。最も丁寧で安全な手段。

### やり方

```bash
git checkout -b maintenance
```

`src/app/page.tsx` と `not-found.tsx` を、シンプルな「メンテナンス中」メッセージに書き換える。可能なら HTTP ステータスを 503 にすると検索エンジンに「一時停止」と伝わる:

```tsx
export const dynamic = "force-static";
export default function Page() {
  return new Response("ただいまメンテナンス中です", {
    status: 503,
    headers: { "Retry-After": "3600" },
  });
}
```

`git push origin maintenance:main` すれば数分で本番反映。

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | メンテナンス中の文言ページ |
| 反映時間 | 5分前後(CF Pages のビルド時間) |
| SEO 影響 | 503 + Retry-After を返せばほぼ無傷。200 で返すと「メンテ画面が本コンテンツ」と誤解される可能性 |
| DNS / SSL | そのまま、何も変わらない |
| 復旧手段 | main を元のコミットに戻して push、または revert |
| 復旧時間 | 再ビルドで 5分前後 |

> **注意:** commit を残す場合、戻すときに `git revert` か `force push` が必要。force push は履歴を書き換えるので、revert(打ち消しコミット)推奨。

### 推奨ワークフロー(3段階)

「平時に準備 → 発動 → 復旧」の3ステップに分けると安全に運用できる。

#### Step 1. 平時の準備(発動前にやっておく)

メンテナンスページは事前に作ってブランチに保管しておく。push してもプレビュー URL ができるだけで本番には影響しない。

```bash
git checkout -b maintenance
# src/app/page.tsx を書き換える
git add . && git commit -m "feat: add maintenance page"
git push origin maintenance
```

CF Pages が自動でプレビュー URL(`maintenance.iamaliar.pages.dev` のような形式)を生成するので、見た目を入念に確認しておく。本番(iamaliar.com)には影響なし。

#### Step 2. 発動(本番をメンテ状態にする)

main にマージして push するだけ。

```bash
git checkout main
git merge maintenance
git push origin main
```

CF Pages が main をビルド → 5分前後で iamaliar.com がメンテ画面に。

#### Step 3. 復旧(本番を戻す)

マージコミットを revert して push。

```bash
git revert <マージコミットのハッシュ>
git push origin main
```

また 5分前後で元のサイトに戻る。

### 運用上のポイント

- プレビュー URL で確認してから本番投入する流れにすると、文言ミスや崩れを防げる
- force push は履歴を書き換えて他の作業に影響するので避ける。revert なら「いつメンテに入れた・戻した」が履歴に残る
- maintenance ブランチは消さず残す。次回からは Step 1 をスキップして Step 2 から実行できる
- ローカルで `npm run dev` または `npm run build && npm start` でも事前確認可能。プレビュー URL より速いがブラウザ・回線による違いは出にくい

## B. Custom domain を一時的に外す

Cloudflare ダッシュボードで iamaliar.com を Pages プロジェクトから外す。即時。

### やり方

- Cloudflare Dashboard → Workers & Pages → iamaliar
- Custom domains タブ
- iamaliar.com の右側「...」→ Remove domain

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | DNS エラー / 404(ブラウザにより表示は様々) |
| 反映時間 | 1分以内 |
| SEO 影響 | 中。検索エンジンが「サイト消滅」と解釈する可能性。短期(数日以内)なら回復可 |
| DNS / SSL | DNS は残るが Pages には届かなくなる。SSL も外れる |
| 復旧手段 | 同画面で iamaliar.com を再追加 |
| 復旧時間 | DNS 反映 1〜数分 + SSL 再発行 5〜15分 |

### こういう時に使う

- セキュリティ事故で「とにかく今すぐ閉じる」必要がある時
- デザイン or 文言が公開状態でマズいことが発覚した時

> **注意:** ユーザーには「壊れた」ようにしか見えない。短時間(15分以内)の対応に向く。長時間止めるなら A(メンテナンスページ)に切り替えること。

## C. Pause deployments(新規ビルドだけ止める)

「現在動いている本番はそのまま、これ以上のデプロイは止めたい」場合の手段。GitHub に push してもビルドが走らなくなる。

### やり方

- Workers & Pages → iamaliar → Settings タブ
- Builds & deployments セクション
- Pause deployments のトグルをオン

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 今動いている本番(変化なし) |
| 反映時間 | 即時 |
| SEO 影響 | なし |
| DNS / SSL | 影響なし |
| 復旧手段 | 同じトグルをオフ |
| 復旧時間 | 即時。次の push でビルドが走る |

### こういう時に使う

- 複数人開発で「今は本番に出したくない PR が main に紛れ込みそう」な時
- リリース直後で問題が出ていないか様子見したい時
- CI が暴走したり想定外のコミットが連投された時の緊急停止

> **注意:** これは「フリーズ」であって「停止」ではない。本番サイトには影響しないので、公開を止める手段としては誤り。

## D. Pages プロジェクトを削除する(完全停止)

もうサイトを運営しない、完全に終わらせる場合。元に戻すには再構築が必要。

### やり方

- Workers & Pages → iamaliar → Settings タブ
- 一番下「Delete project」
- プロジェクト名を入力して確定

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 404 または DNS エラー |
| 反映時間 | 即時 |
| SEO 影響 | 大。検索結果から消える |
| DNS / SSL | Pages 用 DNS レコードは Cloudflare が自動削除 |
| 復旧手段 | GitHub から再連携 → 新規プロジェクト作成 → カスタムドメイン再設定 |
| 復旧時間 | 30分〜1時間(設定再構築 + ビルド + SSL) |

> **注意:** 一時停止には絶対に使わない。終了する時のみ。ドメインそのものは Cloudflare Registrar に残るので、後でまた別のサイトを当てることは可能。

## E. DNS でプロキシ操作する(上級者向け)

Cloudflare の DNS 画面で iamaliar.com の A レコードのプロキシ(オレンジ雲)をオフにしたり、無効な IP に向けたりする手段。あまり推奨しない。

### やり方

- Cloudflare Dashboard → iamaliar.com → DNS → Records
- 対象レコードのプロキシを「DNS only(灰色雲)」に変更、または値を変更

### 挙動

| 項目 | 内容 |
|------|------|
| 訪問者が見るもの | 状況による(DNS エラー / 別のサーバーに到達 / タイムアウト) |
| 反映時間 | 1〜30分(DNS 伝搬) |
| SEO 影響 | 中〜大 |
| DNS / SSL | プロキシオフにすると Cloudflare 経由の保護(WAF, SSL 等)が外れる |
| 復旧手段 | DNS を元に戻す |
| 復旧時間 | 再度 DNS 伝搬待ち |

> **注意:** DNS 操作は影響範囲が読みにくく、設定ミスで長時間サイトが落ちることがある。他に手段がない時の最終手段として。実行前に既存設定のスクショを必ず残すこと。

## ユースケース別の推奨

### ケース1: 数時間〜1日のメンテナンス
→ **A. メンテナンスページ**。訪問者にきちんと状況が伝わる。

### ケース2: 緊急で「とにかく今すぐ閉じたい」(数分内に)
→ **B. Custom domain 外し**。即時で確実。落ち着いてから A に切り替える。

### ケース3: コンテンツの誤字・誤情報をすぐ消したい
→ **Sanity Studio で当該ドキュメントを Unpublish**。サイト停止する必要なし。(60秒以内に CDN キャッシュも切れる)

### ケース4: 本番デプロイを止めて検証したい
→ **C. Pause deployments**。本番は変えずに新規ビルドだけ止まる。

### ケース5: ブランド方針変更で当面サイトを引っ込めたい
→ **A. メンテナンスページ**を「準備中」文言に変えて長期間掲示。数ヶ月単位なら検索エンジンも「コンテンツが変わった」と認識するのでダメージ最小。

### ケース6: サイトを完全に終了する
→ **D. Pages プロジェクト削除**。さらにドメインも手放すなら Cloudflare Registrar から削除。

## FAQ・補足

### Q. 一時停止中も Sanity への課金は発生する?
発生しない。Sanity は API リクエスト数で課金されるので、サイトが止まれば API も叩かれず、自動的に使用量が落ちる。

### Q. 一時停止すると過去のアクセス解析データは消える?
消えない。Cloudflare Web Analytics のデータは Pages プロジェクトとは別管理。ただし D(プロジェクト削除)を選ぶと Pages の Metrics データは消える可能性がある。

### Q. SSL 証明書は止めている間も維持される?
A・C は維持される。B は外れる(再追加で再発行)。D は完全に消える。Cloudflare Universal SSL は無料・自動なので、復活時のコストは時間のみ。

### Q. 一時停止中も GitHub への push はしていい?
OK。A の場合は main の状態が直接サイトになるので注意。C(Pause deployments)中は何度 push してもビルドされないので安全。

### Q. メンテナンス中に Sanity Studio で編集したらどうなる?
編集自体は可能(Sanity は別系統)。ただしサイトが停止中なので、編集結果が表示されるのは復旧後。メンテナンス中にコンテンツも整えておけば、復旧と同時に新コンテンツが見える状態にできる。

### Q. 「短時間だけ止める」の限界は?
B(Custom domain 外し)は復旧時に SSL 再発行で 5〜15分かかるため、5分以下の停止なら止めずにそのまま修正するか、A の事前準備を済ませた方が早い場合が多い。

## 復旧手順テンプレート

### A から復旧

```bash
# main の最新コミット(revert 対象)を確認
git checkout main
git revert <ハッシュ>
git push origin main
# CF Pages が自動再ビルド(5分程度)
```

### B から復旧

- Workers & Pages → iamaliar → Custom domains → Set up a custom domain
- iamaliar.com を入力 → Activate
- ステータスが Active になるまで待つ(5〜15分)
- https://iamaliar.com にアクセスして表示確認

### C から復旧

- Settings → Builds & deployments → Pause deployments をオフ
- 最新コミットが自動で再デプロイされる(または手動で Retry deployment)

### D から復旧

- Workers & Pages → Create application → Pages → Connect to Git
- GitHub の konichiwhatup/iamaliar を選択
- ビルド設定: Framework = Next.js, Build command = `npm run pages:build`, Output = `.vercel/output/static`
- 環境変数を再設定(`NEXT_PUBLIC_SANITY_PROJECT_ID` 等、必要に応じて)
- Custom domain を再追加
- 初回ビルド後、表示確認

### E から復旧

DNS 画面で変更したレコードを元の値に戻す。Pages の DNS レコードは「target.iamaliar.pages.dev」を指す CNAME / CNAME flattening の A レコードが正しい状態。
